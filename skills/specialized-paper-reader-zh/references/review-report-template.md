# 概述
用于对论文进行系统、正式、可复用的详细解读。输出应接近：
- 文献综述笔记
- reviewer 风格评论
- 复现前的技术评估

默认假设用户希望得到的不只是“这篇论文讲了什么”，还包括：
1. 为什么提出这个问题
2. 方法与现有工作相比新在哪里
3. 论文里的关键术语和机制分别是什么意思
4. 实验是否真正支撑作者结论
5. 方法在真实系统、硬件、部署场景中的意义
6. 是否值得跟进、复现或引用

# 总体要求
## 1. 写作风格
- 语言正式、专业、结构化
- 叙述清楚，不堆术语
- 对复杂概念自动补充术语解释，但不削弱专业性
- 尽量使用“论文声称”“实验显示”“从文中证据看”这类措辞区分来源与判断
- 当用户没有特别要求时，默认既做“论文解读”，也做“关键术语说明”

## 2. 证据意识
每一个重要判断都尽量落在论文证据上，例如：
- 章节内容
- 表格结果
- 图示结构
- 消融实验
- 对比实验
- 附录中的训练和实现细节

若论文没有提供足够证据，必须明确指出证据不足。

## 3. 术语解释原则
当论文中出现专业术语、缩写、硬件概念、量化术语、系统术语时，不要默认读者已经熟悉。应在首次出现时，尽量做“轻量但有用”的解释。

术语解释遵循以下原则：

### 3.1 首次出现即解释
当以下内容第一次出现时，优先解释：
- 缩写：如 PTQ、QAT、KV cache、MoE、NoC、PE、SRAM、AWQ、GPTQ、SFC、tiling
- 专业术语：如 activation outlier、memory-bound、operator fusion、dataflow、per-channel quantization
- 指标名：如 TOPS/W、latency、throughput、W8A8、INT4、BF16
- 架构部件：如 systolic array、DMA、scratchpad、runtime、compiler backend
- 组合方法：如“SNDR + Pareto”“LUT + compensation”“LOD + shift + table lookup”“量化 + 校准 + 重建”

### 3.2 解释三层结构
优先用以下三层结构解释术语：

1. **定义**：这个词在该领域里指什么  
2. **在本文中的作用**：它在这篇论文的方法或系统中负责什么  
3. **为什么重要**：它会影响精度、速度、能耗、内存、带宽、面积、可部署性中的什么

若篇幅有限，至少保留前两层。

### 3.3 不要只做字面翻译
错误示例：
- “PTQ 是 post-training quantization，意思是训练后量化。”

正确做法应补足：
- “PTQ 指训练完成后再把模型转成低比特表示，不重新大规模训练。它的优势是部署成本低，但在激活分布复杂或离群值明显时，精度损失可能更大。”

### 3.4 解释要贴合论文上下文
同一个术语在不同论文里关注点可能不同。解释时要优先贴近当前论文。例如：
- 在量化论文里解释 “group-wise quantization” 时，重点说它对量化误差和硬件实现的影响
- 在加速器论文里解释 “tiling” 时，重点说它如何影响片上存储复用和访存开销
- 在系统论文里解释 “operator fusion” 时，重点说它如何减少 kernel launch 或中间张量搬运
- 在硬件近似论文里解释 “SNDR + Pareto” 时，重点说 SNDR 用来筛掉误差主导的不合理位宽配置，Pareto 用来在精度和资源成本之间选保留下来的候选点
- 在查表近似论文里解释 “bipartite LUT” 时，重点说输入如何被拆段、为什么比单大表省存储、以及最后如何组合出近似值

### 3.6 解释组合方法链
当论文把多个方法串成一个方法链时，不要只给一个总称。应尽量拆成：
1. 每个子方法各自是什么  
2. 每个子方法负责解决哪一个局部瓶颈  
3. 它们串联后的完整流程是什么  
4. 这样的组合为什么比 baseline 更适合当前论文目标

### 3.5 控制长度
普通术语解释控制在 1 到 3 句。
关键术语、论文核心机制、用户明显不熟悉的概念，可解释到 3 到 6 句。
不要把正文变成术语词典；只解释对理解论文真正重要的词。

## 4. 领域特化要求
当论文属于以下方向时，启用相应审查重点。

### A. 大模型 / 深度学习方法论文
重点关注：
- 任务设定与问题边界
- 方法机制是否清楚
- 与 baseline 比较是否充分、公平
- 提升来自真正方法创新，还是参数规模/训练资源/数据差异
- 消融是否能支撑每个设计选择

术语重点解释：
- attention、KV cache、MoE、蒸馏、稀疏激活、低秩分解、对齐、token pruning、speculative decoding

### B. 加速器 / NPU / 芯片系统论文
重点关注：
- 工作负载类型与适用边界
- 计算、带宽、缓存、片上存储、调度开销的主瓶颈
- 架构假设是否现实
- 是否只在理想模拟器下成立
- 是否提供面积、功耗、吞吐、时延、能效等完整比较
- 是否区分单算子收益与端到端收益

术语重点解释：
- PE、NoC、SRAM、systolic array、dataflow、tiling、mapping、pipeline、DMA、scratchpad、roofline、memory wall、utilization、throughput、latency、area efficiency、TOPS/W

### C. 模型量化 / 压缩 / 推理优化论文
重点关注：
- 量化策略和粒度
- 误差补偿或重建机制
- 校准/微调/量化感知训练依赖
- 对不同模型规模和任务的泛化
- 实际硬件收益是否被证明
- 是否存在只优化 memory footprint、但未显著优化 latency 的情况

术语重点解释：
- PTQ、QAT、W8A8、W4A8、INT8、INT4、FP8、BF16、per-tensor、per-channel、per-group、activation clipping、outlier、scale、zero-point、dequantization、smooth quant、AWQ、GPTQ、kv cache quantization、mixed precision

# 输出结构
默认输出以下 14 个部分。除非用户明确要求更短，否则不要省略核心部分。整体顺序固定为“结果总览优先，再展开背景、术语、方法与实验”。

## 1. 结果总览
开头必须先总结这篇论文最关键的实验结论。优先回答：
- 相比谁提升了什么
- 提升大致有多大
- 在什么任务 / 数据集 / 硬件 / 设定下成立
- 代价或损失是什么
- 哪组实验最能支撑作者主张

若文中证据不足，必须直接写清：
- 哪些是可确认结论
- 哪些只是作者声称
- 哪些 trade-off 仍不足以判断

## 2. 论文定位
说明：
- 研究主题
- 所属子领域
- 论文想解决的问题类型
- 适合放进什么语境下理解（方法创新、系统优化、硬件设计、部署实用化等）

## 3. 背景与问题定义
详细解释：
- 任务背景
- 为什么这是个问题
- 现有方法的主要不足
- 作者试图填补的空白

这一部分要让没有读过原文的人也能明白论文为什么出现。

## 4. 阅读前必须知道的术语
在正式讲方法前，先列出理解本文最关键的 3 到 8 个术语。
每个术语用如下格式：

- **术语名**
  - 定义：...
  - 在本文中的作用：...
  - 重要性：...

只挑真正影响理解论文的词，不要泛滥罗列。

## 5. 核心思想概述
先正式概括方法主线，再补一段“通俗理解”。
要求回答：
- 方法的输入输出是什么
- 核心机制是什么
- 与传统方案最大的不同是什么
- 作者认为这个设计为什么有效

## 6. 方法细节拆解
这一节必须比“核心思想概述”更细，不能只重复摘要。默认按下面结构讲，必要时可合并相邻小项，但不要省掉“算法怎么做”和“如何落地实现”这两层。

优先使用这样的结构：
- 整体框架：方法由哪几个阶段或模块组成
- 算法原理：核心近似、变换、搜索、补偿或优化到底按什么思路工作
- 算法步骤：每一步的输入、关键变换、输出分别是什么
- 关键模块 1：它具体怎么工作，解决什么问题
- 关键模块 2：它具体怎么工作，解决什么问题
- 与 baseline 的区别：替换了什么、删掉了什么、额外引入了什么
- 软件侧训练 / 搜索 / 校准 / 优化流程：如果论文包含这些过程，要明确写出目标、可训练或可搜索对象、优化方法、输出产物
- 复杂度、代价或实现要求：时间、空间、位宽、存储、控制复杂度、编译依赖等

遇到量化、NPU、加速器类论文时，补充说明：
- 数据流或执行流
- 映射策略
- 精度位宽设计
- 访存与带宽影响
- 编译或 runtime 依赖
- 算法到硬件/系统的映射关系：例如查表、流水线、并行单元、buffer、调度、控制分支、近似单元复用

当某个模块包含高门槛术语时，在对应位置插入：
- **术语解释**：...

当论文属于硬件或系统方向时，优先补充下面两个子问题：
- **算法层面**：这个方法到底按什么规则工作，例如如何分段、如何近似、如何搜索参数、如何补偿误差
- **实现层面**：这些算法步骤是如何映射到硬件或系统中的，例如 LUT、PE、流水线、访存路径、编译调度或 kernel 组织
- **软件层面**：如果有 PyTorch、TensorFlow、脚本搜索、校准或离线优化，需要说明这些软件流程产出了什么参数、表项、阈值或系数，以及这些结果如何被固化到硬件或系统中

如果论文中给出了公式、伪代码、算法框图、结构图，优先利用这些证据来解释，不要只说“作者采用了某方法”。
如果某个近似方法背后隐含了常见思想，例如一阶线性近似、分段近似、主表 + 修正表、误差补偿、离线搜索、查表复用，应主动讲明，不要只照抄论文名词。

## 7. 论文的创新点
分成两层：
- 作者声称的创新点
- 结合相关工作后较可信的创新点

然后判断创新类型属于：
- 新任务定义
- 新模型结构
- 新训练策略
- 新量化/压缩机制
- 新硬件架构
- 新系统实现
- 工程整合优化
- 主要是已有方法组合

若创新更偏工程实现而非理论突破，要直接说明。

## 8. 实验设置
总结实验如何设计，包括：
- 数据集或工作负载
- baseline
- 指标
- 硬件/软件环境
- 训练或部署设定
- 消融实验设计

重点检查：
- baseline 是否足够强
- 对比是否公平
- 评价指标是否与论文目标一致
- 是否缺少最关键的对照组

## 9. 结果解读
不要只复述结果，要解释结果意味着什么。包括：
- 哪些结果最关键
- 哪些结果真正支持论文主张
- 是否存在“提升有限但叙述夸大”
- 是否有 trade-off，例如精度下降、面积增加、功耗升高、编译成本增加、延迟恶化等

对于硬件/系统论文，特别注意：
- 峰值指标和端到端指标是否混淆
- 模拟结果和真实芯片/真实部署结果是否混淆

## 10. 关键术语与机制回看
在讲完整篇论文后，再回看 3 到 5 个最关键术语或机制。
要求说明：
- 它们在论文中真正发挥了什么作用
- 哪些只是包装性表述，哪些是实质性贡献
- 这些术语是否对应真实系统收益
- 如果某个术语背后其实是一整条方法链，要再次点明这条链里每个环节分别负责什么

这一节用于防止只“懂名词”，却没看清其实际作用。

## 11. 优点
列出最重要的优点，并解释为什么这些优点重要。
优点可以来自：
- 问题重要
- 方法直观且有效
- 工程实现扎实
- 实验比较全面
- 对实际部署有参考价值

## 12. 局限、风险与疑点
这一部分必须具体，不要泛泛而谈。
优先检查：
- 适用范围是否窄
- 假设是否强依赖特定硬件、特定模型、特定数据分布
- 消融不充分
- baseline 不公平
- 缺少真实系统验证
- 复现门槛高
- 对工业场景收益可能被高估

## 13. 可复现性与落地性评估
单独评估：
- 论文是否给出足够实现细节
- 是否公开代码、配置、校准方式或硬件设定
- 复现主要难点是什么
- 更接近“学术指标优化”还是“可工程落地方案”

对于量化/加速器/NPU论文，额外判断：
- 是否需要定制 kernel、编译器或硬件支持
- 是否只能在特定 batch、序列长度、模型结构下收益明显
- 是否容易迁移到真实产品

## 14. 总体评价与阅读建议
先给出正式的总结性判断，再根据不同目标给建议。

总结性判断例如：
- 是一篇问题明确、实验扎实、具有参考价值的工作
- 方法有一定启发，但证据不足以支撑其强结论
- 更像工程优化而非根本性创新
- 对特定硬件/部署场景很有价值，但通用性有限

阅读建议包括：
- 做组会汇报，重点看哪里
- 做综述，重点提炼什么
- 做复现，先关注哪些细节
- 做产品/芯片/NPU 方案评估，最该关注哪些约束

# 通俗解释规则
当论文包含较高理解门槛时，在对应段落追加“通俗解释”：
- 用 2 到 4 句说明本质
- 不使用幼稚比喻
- 不改变原意
- 不引入论文中没有的机制
- 通俗解释必须服务于论文理解，而不是泛泛科普

建议用这样的句式：
- “通俗地说，这里的核心不是……，而是……”
- “从实现角度看，它本质上是在……”
- “这一步可以理解为把……换成了更适合……的表示/执行方式”
- “它真正解决的问题不是精度本身，而是……约束下的……问题”

# 针对 AI / NPU / 加速器 / 量化论文的附加小节
若论文与部署、芯片或系统实现强相关，在末尾额外输出：

## 对芯片 / NPU / 部署团队的启发
从以下角度简要总结：
- 对硬件架构设计的启发
- 对编译器或运行时的启发
- 对量化部署链路的启发
- 对真实产品落地的限制

# 禁止事项
- 不要只按摘要改写成长文
- 不要默认作者比较对象就是最合理 baseline
- 不要因为结果表多就认定实验充分
- 不要把模拟器结果自动等同真实硬件收益
- 不要在缺乏 related work 对照时断言“很有创新”
- 不要忽略部署条件、内存约束、带宽瓶颈、编译成本等现实因素
- 不要把术语解释写成词典摘录，必须贴合论文上下文
- 不要解释一堆边缘名词，却漏掉真正决定论文价值的核心机制
